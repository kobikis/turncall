TurnCall supports browser-based voice calls via WebRTC using Pipecat's SmallWebRTCTransport. Audio flows peer-to-peer at 16kHz.

## SDP Signaling

### Connect

Send an SDP offer and receive an answer:

```bash
curl -X POST http://localhost:8090/v1/webrtc/connect \
  -H "Authorization: Bearer tc_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "sdp": "v=0...",
    "type": "offer",
    "requestData": {
      "agent_id": "AGENT_UUID"
    }
  }'
```

The answer carries the **call id** alongside the SDP:

```json
{
  "sdp": "v=0...",
  "type": "answer",
  "call_id": "CALL_UUID"
}
```

That is the handle for everything after the call — its transcript, its recording, or converting it into an [eval scenario](/guides/evals). A client that only reads `sdp` and `type` is unaffected.

If the agent cannot start (a provider with no key, say), there is no answer to give: the response is `500` with code `pipeline_start_failed`, the reason, and `details.missing_keys` when keys are missing. The call is recorded as `failed`.

```json
{
  "success": false,
  "code": "pipeline_start_failed",
  "error": "The agent could not start (call CALL_UUID): No API key for deepgram: add it as a project credential or set it in the platform environment",
  "details": {"missing_keys": ["deepgram"]}
}
```

A call that does start and then loses a provider ends like any other from the browser's side. Its `error.raised` event says why; see [When a call fails](/guides/post-call-analysis#when-a-call-fails).

### ICE Trickle

```bash
curl -X PATCH http://localhost:8090/v1/webrtc/connect \
  -H "Authorization: Bearer tc_xxx" \
  -H "Content-Type: application/json" \
  -d '{"candidate": "...", "sdpMid": "0", "sdpMLineIndex": 0}'
```

## Dynamic Routing

Pass `server_url` in `requestData` for pre-call initialization:

```json
{
  "sdp": "v=0...",
  "type": "offer",
  "requestData": {
    "server_url": "https://your-server.com/turncall/init"
  }
}
```

See [Pre-Call Init](/guides/call-init) for response format.
