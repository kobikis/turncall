Pre-call initialization lets you dynamically select and configure the agent before a call starts. Works on all transports.

## Supported Transports

| Transport | Trigger | `call.type` value |
|-----------|---------|-------------------|
| Twilio voice | `routing_target_type: "webhook"` on phone number | `inboundPhoneCall` |
| Outbound phone call (API or campaign) | caller-ID number has `routing_target_type: "webhook"` | `outboundPhoneCall` |
| WhatsApp voice | `routing_target_type: "webhook"` on phone number | `inboundWhatsAppCall` |
| WebRTC | `server_url` in POST /v1/webrtc/connect body | `webrtc` |
| SMS | `routing_target_type: "webhook"` + `sms_enabled` on phone number | `inboundSms` |
| WhatsApp text | `routing_target_type: "webhook"` + `whatsapp_enabled` on phone number | `inboundWhatsAppMessage` |

## Setup

### Phone numbers (Twilio / WhatsApp)

Bind with `routing_target_type: "webhook"`:

```bash
curl -X POST http://localhost:8090/v1/phone-numbers \
  -H "Authorization: Bearer tc_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "e164_number": "+15551234567",
    "external_number_sid": "PNxxx",
    "routing_target_type": "webhook",
    "server_url": "https://your-server.com/turncall/init"
  }'
```

### WebRTC

Pass `server_url` in `requestData`:

```json
POST /v1/webrtc/connect
{
  "sdp": "v=0...",
  "type": "offer",
  "requestData": {
    "server_url": "https://your-server.com/turncall/init"
  }
}
```

```json
      "type": "inboundPhoneCall"
    },
    "phoneNumber": {"number": "+15551234567"},
    "customer": {"number": "+15559876543"},
    "timestamp": "2026-04-06T12:00:00Z"
  }
}
```

### Outbound calls

An outbound call placed from a webhook-routed number (`POST /v1/calls/outbound`
or a campaign) runs call-init too, at the dial, before the phone rings. The
roles are the same as inbound: `phoneNumber` is your number, `customer` the
person called. `call` also carries `agent_id`, the agent the dial named, and
`variables`, the dial's (a campaign target's) template variables, when it has
any. `provider_call_id` is empty: nothing has been dialled yet.

- Your answer's `agent_id` (an agent in the same project) or inline `agent`
  runs the call; with neither, the dial's agent does.
- Your `variables` are merged under the dial's: on a clash the dial's value
  wins. Your `metadata` is stored as on an inbound call (the call's
  `metadata.metadata`), and `knowledge_context` likewise.
- A call-init that fails, times out, or names an agent that cannot run (an
  invalid inline config, an `agent_id` that is not one of the project's) does
  not stop the dial: the dial's agent runs with the dial's own variables and
  metadata, none of your answer, and a warning is logged.
- Call-init runs after the project's limits admit the dial, so a refused dial
  never reaches your server.

A number with any other routing never runs call-init.

### Text conversations (SMS, WhatsApp text)

A text to a webhook-routed number runs call-init **once per conversation**: on
the message that opens a session, never on the ones after it. `call.id` is the
id the session is created with (the `session_id` of its events), `call.type`
is `inboundSms` or `inboundWhatsAppMessage`, and `provider_call_id` is empty.

- Your answer's `agent_id` (an agent in the number's project) or inline `agent`
  answers the conversation. An inline agent has no agent row: the session's
  `agent_id` is null, and its config is never shown by the API.
- `variables`, `metadata` and `knowledge_context` are kept on the session and
  apply to every reply in it, as they do for a whole call.
- A call-init that fails, times out, or names no agent that can run leaves the
  message unanswered (an SMS gets a short apology) and opens no session; the
  next message asks again.
- The session expires after 24 hours without a message; the next text opens a
  new one, and asks again.

## Verify the Signature

Each call-init request is HMAC-signed with the number's `server_url_secret` (returned when you [bind the number](/guides/phone-numbers)). Headers: `X-TurnCall-Signature: v1=<hex>` and `X-TurnCall-Timestamp`; the HMAC-SHA256 is computed over `"{timestamp}.{raw_body}"` — the same scheme as [event webhooks](/guides/server-events).

```python
import hashlib, hmac

def verify(raw_body: str, sig: str, ts: str, secret: str) -> bool:
    expected = "v1=" + hmac.new(
        secret.encode(), f"{ts}.{raw_body}".encode(), hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected, sig)
```

Reject unverified requests — call-init decides which agent answers a real call.

## Response Fields

| Field | Purpose |
|-------|---------|
| `agent_id` | Load existing agent by UUID |
| `agent` | Inline agent config (alternative to `agent_id`) — see below |
| `variables` | Template variables rendered into `{{placeholders}}` in prompts |
| `metadata` | Stored on call record for analytics |
| `dynamic_data.knowledge_context` | Prepended to system prompt as runtime context |

## Returning an inline agent

`agent` and `agent_id` are alternatives, not a merge: an inline `agent`
**replaces** the configuration for that call rather than overriding parts of a
stored one. Send the whole config, not a patch.

Because an inline agent is not a stored agent, it has no row to point at, and
that is visible to you:

<Warning>
  Every event for such a call carries `agent_id: null`, and the call does not
  appear in per-agent listings. This is the correct answer to "which stored
  agent ran this call" — `null` means *none of them*, not *not resolved yet*.
</Warning>

Everything else still works. The configuration the call ran with is recorded on
the call itself, so post-call analysis, the transcript and the `call.ended`
webhook are unaffected. Correlate such calls through `call_id`, or through
`metadata` you returned in the call-init response — that is what it is for.

Knowledge bases linked to a *stored* agent do not apply, since the call does not
run that agent. An inline agent names its own in `knowledge_bases`, with the
same fields as a link (`knowledge_base_id`, `mode`, `priority`, `top_k`,
`similarity_threshold`, `tool_description`):

```json
{
  "agent": {
    "system_prompt": "You are the receptionist at Luigi's.",
    "knowledge_bases": [{"knowledge_base_id": "KB_ID", "mode": "prompt"}]
  }
}
```

Each id must be a knowledge base in the phone number's project. One that is
not, or an entry TurnCall cannot read, is skipped with a warning and the call
still connects. See [Knowledge Base](/guides/knowledge-base#inline-agents).

<Tip>
  For persistent, searchable knowledge, use the [Knowledge Base API](/guides/knowledge-base) instead of `knowledge_context`. Use `knowledge_context` for per-call dynamic data like CRM records or open tickets.
</Tip>
