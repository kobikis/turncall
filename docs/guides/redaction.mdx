---
title: Redaction
description: "Replace callers' phone numbers, emails and card numbers in everything a project stores and sends"
icon: "eye-slash"
---

With redaction on, PII in a project's calls is replaced before it is stored or sent: in the transcript, on the call's event log and in every webhook. A caller who says "my number is 415 555 0132" reads back as "my number is `<PHONE_NUMBER>`".

The agent is never redacted. The model hears the caller's words and can book the appointment with the number it was given. A warm transfer's operator is briefed on them, and post-call analysis and takeaways read them. Only what they produce is redacted on the way out.

Detection runs inside your deployment, with [Presidio](https://microsoft.github.io/presidio/) and spaCy's small English model. No text is sent to a vendor to be redacted.

## Turn it on

```bash
curl -X PUT https://api.example.com/v1/projects/$PROJECT_ID/redaction \
  -H "Authorization: Bearer tc_..." \
  -H "Content-Type: application/json" \
  -d '{"enabled": true}'
```

This needs an admin key, and a project can only set its own. The `PUT` replaces the whole setting, so `enabled` is required: a body without it is a `422`. The project read (`GET /v1/projects/{id}`) shows it under `redaction`.

A change applies to what is stored or sent next, including on a call that is already live: at once on the server that took the `PUT`, and within 30 seconds on your other servers, which cache the setting for that long. Nothing stored before it is rewritten. For a call that was already live, the lines stored before the change stay as they were, in the transcript read and in that call's `call.ended`.

Turning it on also starts loading the detector in the background, which takes a few seconds. A server that starts while any project has redaction on loads it at startup.

## Entity types

`entities` chooses what to replace. Leave it out, or send `null`, to get the default:

| Type | Example |
|------|---------|
| `PHONE_NUMBER` | 415 555 0132 |
| `EMAIL_ADDRESS` | jane.doe@example.com |
| `CREDIT_CARD` | 4111 1111 1111 1111 |
| `US_SSN` | 536-22-8726 |
| `IBAN_CODE` | GB82 WEST 1234 5698 7654 32 |

You can also choose `PERSON`, `LOCATION`, `DATE_TIME`, `ORGANIZATION`, `URL`, `IP_ADDRESS`, `US_BANK_NUMBER`, `US_DRIVER_LICENSE`, `US_PASSPORT`, `US_ITIN`, `UK_NHS`, `MEDICAL_LICENSE`, `CRYPTO`, `MAC_ADDRESS`, `AGE` and `NRP`. An unknown name is a `422`.

```json
{"enabled": true, "entities": ["PHONE_NUMBER", "EMAIL_ADDRESS", "PERSON"]}
```

`PERSON` is not in the default because the small model gets names wrong. "Hi, this is Ava from Acme Dental" becomes "Hi, this is Ava from `<PERSON>`": the company is taken for a person, and the name is missed.

## What is redacted

- **The transcript**: `GET /v1/calls/{id}/transcript`, and `transcript` in `call.ended`.
- **Every call event**: on the event log (`GET /v1/calls/{id}/events`) and in every webhook. That includes tool arguments and results in `tool.result`, and a call's `metadata` in `call.ended`. A JSON number of seven digits or more inside them is analysed as the digits it is written with, as in tool invocations below: `{"phone": 4155550132}` reads `{"phone": "<PHONE_NUMBER>"}`.
- **The numbers in payloads**: see [Number fields](#number-fields). The call record keeps them: `GET /v1/calls/{id}` still shows `from_number`, and routing, the suppression list and campaigns work as before.
- **Post-call analysis and takeaways**: stored redacted on the call, so `analysis` on `GET /v1/calls/{id}` and `GET /v1/calls/{id}/analysis` match `summary` and `analysis` in `call.ended`. A takeaway's fields, and `structured_data`'s, are yours, so every value is analysed whatever its field is called: a field named `customer_id` or `callback_url` is redacted like any other.
- **Tool invocations**: the arguments (`input_json`) and the result (`output_json`) of every tool call are stored redacted, so `GET /v1/tools/invocations/{call_id}` and a chat session's invocations read back redacted. As with takeaways, the fields are the tool's, and every value is analysed. A JSON number of seven digits or more is analysed as the digits it is written with: `{"card_number": 4111111111111111}` is stored as `{"card_number": "<CREDIT_CARD>"}`, while an order number the detector finds nothing in stays a number. The status is read from the result before it is redacted. Your tool's webhook still gets the raw arguments during the call, and the model the raw result. A scenario drafted from a call or a session (`POST /v1/eval-scenarios/from-call`, `/from-session`) is built from these records and the transcript, so its arguments and tool mocks are redacted too.
- **Logs and traces**: see [below](#logs-and-traces).
- **Text conversations** (SMS, WhatsApp and the Chat API): see [below](#text-conversations).

TurnCall's own identifiers are never analysed: ids, timestamps, statuses, provider names (the `from` and `to` of `provider.failover`), tool names (`tool_name`) and skill names, versions and load reasons (`skill.loaded`, and `skills` on `call.ended`), and procedure names and step ids (`procedure.step`, `procedure.refused`, `procedure.left`, and `procedures` on `call.ended`). With `ORGANIZATION` chosen, "Azure" in a provider name stays as it is.

Not yet redacted: the call record's own `metadata` and numbers (the numbers stay on purpose, see above).

Never redacted: call-init and tool webhooks. These are part of the live call, and your own server answers them with the raw values.

## Number fields

With `PHONE_NUMBER` chosen (it is in the default), these fields at the top of a payload are replaced whole by `<PHONE_NUMBER>`, on every event and webhook that carries them, your own TurnCall number included:

`from_number`, `to_number`, `customer_number`, `turncall_number`, `target_number`, `number`

A field is replaced whole only when its value is a string that is a phone number and nothing else: digits with an optional `+`, spaces, dots, dashes and brackets, at least seven digits, after an optional scheme such as `tel:` or `whatsapp:` (`+1 (415) 555-0132`, `whatsapp:+14155550132`, a WhatsApp id). That needs no detector, so it holds while the detector is unavailable.

Any other value in these fields is analysed as text, like every other string: a WebRTC call's `"webrtc"`, a SIP address such as `sip:+14155550132@pbx.example.com`, a short code of fewer than seven digits. The detector decides what it finds there, so a SIP address is not guaranteed to read `<PHONE_NUMBER>`, and while the detector is unavailable such a value reads `<REDACTED>`. A field with one of these names deeper in a payload (inside `metadata` or a tool's arguments) is analysed as text too.

Without `PHONE_NUMBER` chosen, a value that is a phone number stays as it is.

## Logs and traces

The server's log lines and OpenTelemetry spans about a redacting project's calls and text conversations are redacted before they leave the process. That covers the carrier webhooks' lines (the caller's `from_number`), the call's pipeline (the observers log what was said, and the STT, LLM and TTS spans carry the transcript and the model's input and output), tool calls, transfers, post-call analysis, SMS and WhatsApp messages, and every API request made with the project's key.

This is not the detector. A log line is written on the path that carries the call's audio, where the detector's hundreds of milliseconds would stall it, so logs and spans are redacted with regular expressions for the types that have a fixed shape: `PHONE_NUMBER`, `EMAIL_ADDRESS`, `CREDIT_CARD` (Luhn-checked), `US_SSN` and `IBAN_CODE` (checksum-validated), each only if the project chose it. Any other type, `PERSON` or `LOCATION` say, is not found in logs and spans. Ids and timestamps are never touched.

How a number is told from everything else that is digits:

- **Several numbers side by side are found one by one.** "4155550132 4155550133" is two phone numbers, not one 20-digit run too long to be either. A run too long for one number is split at its spaces, and from each group on the longest stretch that reads as a number is replaced, so a digit too many may be redacted with it ("+44 20 7946 0958 123 456" becomes "`<PHONE_NUMBER>` 456") but never one too few.
- **A number inside an address is still a number.** With `PHONE_NUMBER` chosen and `EMAIL_ADDRESS` not, a WhatsApp id written `14155550132@s.whatsapp.net` or a SIP address `sip:+14155550132@pbx.example.com` has its number replaced and keeps the rest. With `EMAIL_ADDRESS` chosen, the whole address is.
- **Timestamps and long ids are not numbers.** A bare run of digits (no `+`, no separators) is a phone number at 10 to 15 digits, but one starting with `1` only at 11 digits (`+1` and ten: no other country code starts with 1, and no US area code does). A bare card number starts with 2 to 6, as every major network's do (or is a 15-digit UATP number starting with 1). So epoch timestamps, which start with 1 in seconds, milliseconds, microseconds or nanoseconds (`1760000000123`), and ids padded with zeros are left as they are. A bare 11- to 15-digit id starting with 2 to 9 does read as a phone number: a WhatsApp id looks exactly like it.
- **Separated, a phone number has a group of three digits or more** ("10 20 30 40" is a list), and one written with dots must read like `415.555.0132` (not a version, a decimal or an IP address).

- **Exceptions**: for a redacting project, a logged exception's traceback is written without the local variables loguru would otherwise show, redacted and appended to the message. In JSON logs, its `exception` field is `null`.
- **Spans**: a span started during the project's call is marked `turncall.redaction` (the chosen types), and its attributes, event attributes and status description are redacted as it is exported. The call's `turncall.from_number` and `turncall.to_number` are left off its spans altogether, whatever `PIPECAT_TRACE_INCLUDE_PII` says.
- **What is outside a project** is logged as before: startup, a webhook for a number no project owns, a request without a valid key.
- **A call follows the setting it started with.** Logs and spans read the project's setting when the call (or the request, or the text message) starts, not on every line.

## Text conversations

An SMS, WhatsApp or Chat API session works differently from a call, because its agent rereads the stored messages on every turn. If they were stored redacted, the agent would forget the number it was given one message earlier. So while a session is live, its messages are stored as written, and everything that reads them is redacted:

- `GET /v1/chat/sessions/{id}/messages`: each message's `content`. A page is redacted before it is answered, a few dozen messages at a time so a long conversation does not hold up live calls' redaction, and holds at most 500 (a larger `limit` is cut to 500, as the response's `limit` shows; the same holds for `GET /v1/chat/sessions`).
- `GET /v1/chat/sessions` and `GET /v1/chat/sessions/{id}`: `customer_number` and `turncall_number` (with `PHONE_NUMBER` chosen; a Chat API session's `api` stays as it is).
- `POST /v1/eval-scenarios/from-session`: the derived scenario, as `/from-call` reads a call's redacted transcript.
- The `chat.created` and `session.*` webhooks.

Once a session ends, the agent never reads it again, so its messages and numbers are rewritten redacted in the database, as a call's are stored. A session ends when it expires (24 hours after its last message), when you `DELETE /v1/chat/sessions/{id}`, or when a new session replaces it. The rewrite runs in the session sweep, every 15 minutes, and covers sessions that ended while the project had redaction on. Every server runs the sweep; each claims the sessions it rewrites, so no session is rewritten twice, and a claim lapses after ten minutes if its server dies mid-rewrite. A reply that finishes after its session ended, as it is being rewritten, is stored and the session is rewritten again at the next sweep. A session that ended before redaction was turned on is not rewritten, but while redaction is on its reads are redacted all the same. If the detector cannot answer, the rewrite waits for the next sweep rather than storing `<REDACTED>`.

The reply to `POST /v1/chat` and the text sent to the customer by SMS or WhatsApp are the live conversation, so they are never redacted.

## Limits

- **Recall is the detector's.** It finds what the STT wrote as digits. "Four one five, five five five…" spelled out in words is missed, and so is "jane dot doe at example dot com". Deepgram's default formatting writes digits; check your STT provider's.
- **English only.**
- **Text only.** The recording is not bleeped. Every voice call is recorded and there is no setting that turns it off, so if recordings hold PII, keep them for a short time with `recordings_days` (see [Retention](/guides/retention)).
- **Briefings and analysis read from memory.** The server that ran the call holds the conversation for five minutes after it ends, and nowhere else: it is never written to Redis or the database. When the carrier's callback or the call's end lands on another server, that server asks the one holding the conversation to build the briefing or run the analysis (over Redis, naming only the call). When no server holds it any more (a restart, after the five minutes, or `POST /v1/calls/{id}/analysis/rerun` later on), they read the stored, redacted transcript instead, and the server logs `transfer_briefing_from_stored_transcript` or `post_call_analysis_from_stored_transcript`.
- **When the detector can't keep up, text is withheld.** It never goes out raw. If the detector fails to load, every analysed string becomes `<REDACTED>` for five minutes (logged once, as `redaction_unavailable`), then the load is tried again. If a server falls far behind, text is withheld rather than queued (`redaction_backlog_full_withheld`), and a redaction that takes over a second is logged as `redaction_slow`.
- **It runs in a process of its own.** Each server runs the detector in one worker process, which holds about 200 MB once loaded, so its CPU work stays out of the process that carries live calls' audio.
