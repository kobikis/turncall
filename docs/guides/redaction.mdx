---
title: Redaction
description: "Replace callers' phone numbers, emails and card numbers in everything a project stores and sends"
icon: "eye-slash"
---

With redaction on, PII in a project's calls is replaced before it is stored or sent: in the transcript, on the call's event log and in every webhook. A caller who says "my number is 415 555 0132" reads back as "my number is `<PHONE_NUMBER>`".

The agent is never redacted. The model hears the caller's words and can book the appointment with the number it was given. A warm transfer's operator is briefed on them, and post-call analysis and takeaways read them. Only what they produce is redacted on the way out.

Detection runs inside your deployment, with [Presidio](https://microsoft.github.io/presidio/) and spaCy's small English model. No text is sent to a vendor to be redacted.

## Turn it on

```bash
curl -X PUT https://api.example.com/v1/projects/$PROJECT_ID/redaction \
  -H "Authorization: Bearer tc_..." \
  -H "Content-Type: application/json" \
  -d '{"enabled": true}'
```

This needs an admin key, and a project can only set its own. The `PUT` replaces the whole setting, so `enabled` is required: a body without it is a `422`. The project read (`GET /v1/projects/{id}`) shows it under `redaction`.

A change applies to what is stored or sent next, including on a call that is already live: at once on the server that took the `PUT`, and within 30 seconds on your other servers, which cache the setting for that long. Nothing stored before it is rewritten. For a call that was already live, the lines stored before the change stay as they were, in the transcript read and in that call's `call.ended`.

Turning it on also starts loading the detector in the background, which takes a few seconds. A server that starts while any project has redaction on loads it at startup.

## Entity types

`entities` chooses what to replace. Leave it out, or send `null`, to get the default:

| Type | Example |
|------|---------|
| `PHONE_NUMBER` | 415 555 0132 |
| `EMAIL_ADDRESS` | jane.doe@example.com |
| `CREDIT_CARD` | 4111 1111 1111 1111 |
| `US_SSN` | 536-22-8726 |
| `IBAN_CODE` | GB82 WEST 1234 5698 7654 32 |

You can also choose `PERSON`, `LOCATION`, `DATE_TIME`, `ORGANIZATION`, `URL`, `IP_ADDRESS`, `US_BANK_NUMBER`, `US_DRIVER_LICENSE`, `US_PASSPORT`, `US_ITIN`, `UK_NHS`, `MEDICAL_LICENSE`, `CRYPTO`, `MAC_ADDRESS`, `AGE` and `NRP`. An unknown name is a `422`.

```json
{"enabled": true, "entities": ["PHONE_NUMBER", "EMAIL_ADDRESS", "PERSON"]}
```

`PERSON` is not in the default because the small model gets names wrong. "Hi, this is Ava from Acme Dental" becomes "Hi, this is Ava from `<PERSON>`": the company is taken for a person, and the name is missed.

## What is redacted

- **The transcript**: `GET /v1/calls/{id}/transcript`, and `transcript` in `call.ended`.
- **Every call event**: on the event log (`GET /v1/calls/{id}/events`) and in every webhook. That includes tool arguments and results in `tool.result`, and a call's `metadata` in `call.ended`.
- **The numbers in payloads**: with `PHONE_NUMBER` chosen, `from_number`, `to_number`, `customer_number`, `turncall_number`, `target_number` and `number` are replaced whole. The call record keeps them: `GET /v1/calls/{id}` still shows `from_number`, and routing, the suppression list and campaigns work as before.
- **Post-call analysis and takeaways**: stored redacted on the call, so `analysis` on `GET /v1/calls/{id}` and `GET /v1/calls/{id}/analysis` match `summary` and `analysis` in `call.ended`. A takeaway's fields, and `structured_data`'s, are yours, so every value is analysed whatever its field is called: a field named `customer_id` or `callback_url` is redacted like any other.
- **Tool invocations**: the arguments (`input_json`) and the result (`output_json`) of every tool call are stored redacted, so `GET /v1/tools/invocations/{call_id}` and a chat session's invocations read back redacted. As with takeaways, the fields are the tool's, and every value is analysed. The status is read from the result before it is redacted. Your tool's webhook still gets the raw arguments during the call, and the model the raw result. A scenario drafted from a call or a session (`POST /v1/eval-scenarios/from-call`, `/from-session`) is built from these records and the transcript, so its arguments and tool mocks are redacted too.
- **Logs and traces**: see [below](#logs-and-traces).

TurnCall's own identifiers are never analysed: ids, timestamps, statuses, provider names (the `from` and `to` of `provider.failover`) and tool names (`tool_name`). With `ORGANIZATION` chosen, "Azure" in a provider name stays as it is.

Not yet redacted: the call record's own `metadata` and numbers (the numbers stay on purpose, see above), SMS and chat messages.

Never redacted: call-init and tool webhooks. These are part of the live call, and your own server answers them with the raw values.

## Logs and traces

The server's log lines and OpenTelemetry spans about a redacting project's calls and text conversations are redacted before they leave the process. That covers the carrier webhooks' lines (the caller's `from_number`), the call's pipeline (the observers log what was said, and the STT, LLM and TTS spans carry the transcript and the model's input and output), tool calls, transfers, post-call analysis, SMS and WhatsApp messages, and every API request made with the project's key.

This is not the detector. A log line is written on the path that carries the call's audio, where the detector's hundreds of milliseconds would stall it, so logs and spans are redacted with regular expressions for the types that have a fixed shape: `PHONE_NUMBER`, `EMAIL_ADDRESS`, `CREDIT_CARD` (Luhn-checked), `US_SSN` and `IBAN_CODE` (checksum-validated), each only if the project chose it. Any other type, `PERSON` or `LOCATION` say, is not found in logs and spans. Ids and timestamps are never touched.

- **Exceptions**: for a redacting project, a logged exception's traceback is written without the local variables loguru would otherwise show, redacted and appended to the message. In JSON logs, its `exception` field is `null`.
- **Spans**: a span started during the project's call is marked `turncall.redaction` (the chosen types), and its attributes, event attributes and status description are redacted as it is exported. The call's `turncall.from_number` and `turncall.to_number` are left off its spans altogether, whatever `PIPECAT_TRACE_INCLUDE_PII` says.
- **What is outside a project** is logged as before: startup, a webhook for a number no project owns, a request without a valid key.
- **A call follows the setting it started with.** Logs and spans read the project's setting when the call (or the request, or the text message) starts, not on every line.

## Limits

- **Recall is the detector's.** It finds what the STT wrote as digits. "Four one five, five five five…" spelled out in words is missed, and so is "jane dot doe at example dot com". Deepgram's default formatting writes digits; check your STT provider's.
- **English only.**
- **Text only.** The recording is not bleeped. If it holds PII, turn recording off or keep it for a short time.
- **Briefings and analysis read from memory.** The server that ran the call holds the conversation for five minutes after it ends, and nowhere else: it is never written to Redis or the database. When the carrier's callback or the call's end lands on another server, that server asks the one holding the conversation to build the briefing or run the analysis (over Redis, naming only the call). When no server holds it any more (a restart, after the five minutes, or `POST /v1/calls/{id}/analysis/rerun` later on), they read the stored, redacted transcript instead, and the server logs `transfer_briefing_from_stored_transcript` or `post_call_analysis_from_stored_transcript`.
- **When the detector can't keep up, text is withheld.** It never goes out raw. If the detector fails to load, every analysed string becomes `<REDACTED>` for five minutes (logged once, as `redaction_unavailable`), then the load is tried again. If a server falls far behind, text is withheld rather than queued (`redaction_backlog_full_withheld`), and a redaction that takes over a second is logged as `redaction_slow`.
- **It runs in a process of its own.** Each server runs the detector in one worker process, which holds about 200 MB once loaded, so its CPU work stays out of the process that carries live calls' audio.
