Agents are the core unit in TurnCall. An agent defines the personality, voice, and capabilities of your AI assistant.

## Create an Agent

```bash
curl -X POST http://localhost:8090/v1/agents \
  -H "Authorization: Bearer tc_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "receptionist",
    "config": {
      "system_prompt": "You are a dental clinic receptionist...",
      "first_message": "Thank you for calling! How can I help?",
      "stt": {"provider": "deepgram", "model": "nova-3-general", "language": "en"},
      "llm": {"provider": "openai", "model": "gpt-5.4-mini"},
      "tts": {"provider": "deepgram", "voice": "aura-2-helena-en"}
    }
  }'
```

## Agent Config

```json
{
  "name": "receptionist",
  "config": {
    "system_prompt": "You are a helpful receptionist...",
    "first_message": "Hello! How can I help?",
    "stt": {"provider": "deepgram", "model": "nova-3-general", "language": "en"},
    "llm": {"provider": "openai", "model": "gpt-5.4-mini"},
    "tts": {"provider": "deepgram", "voice": "aura-2-helena-en"},
    "tools": [],
    "mcp_servers": [],
    "skills": [{"skill": "verify_identity"}],
    "silence_timeout_ms": 800,
    "interruption_enabled": true,
    "smart_turn_detection": true,
    "voicemail_detection": {
      "enabled": true,
      "voicemail_message": "Please call us back..."
    },
    "server_url": {
      "url": "https://your-server.com/events",
      "events": ["*"]
    }
  }
}
```

<Note>
  Agents using the `bedrock` LLM provider or the `aws` S2S provider also take a
  top-level `aws` block for region and credentials — one per agent, shared by
  both. See [AWS credentials](/guides/providers#credentials).
</Note>

`skills` names the project's [skills](/guides/skills) the agent may load
mid-call. The model sees each one's name and description, and loads one with
the built-in `load_skill` tool when the conversation needs it.
`max_loaded_skills` (default 3, 1 to 10) caps how many it holds loaded at
once; loading one more unloads the one loaded longest ago. An entry follows
the skill's live published version, so a skill publish reaches the agent's
next call without republishing it, unless the entry pins one with `version_id`
(see [Pin a version](/guides/skills#pin-a-version)). Each name must have a
published version in the project (a pin: a published or archived version of
that skill), and no skill
tool may share a name with a built-in, the agent's own tool or another listed
skill's tool: saving the agent otherwise is a `422` naming both sides (see
[Skills](/guides/skills#attach-skills-to-an-agent)).

## Procedures

A **procedure** is a graph of steps the agent follows on a call: diagnostic
questions in order, checks the caller performs, the conditions that decide
the next step, and where it ends. TurnCall holds the route; on every caller
turn the model is shown only a **window** of it, and reports each move.

```json
"procedures": [
  {
    "name": "no_internet",
    "description": "Caller has no internet connection at home",
    "start": "call",
    "window_depth": 1,
    "steps": [
      {"id": "lights", "kind": "ask", "start": true,
       "text": "Ask which lights on the router are on and their colour.",
       "moves": [
         {"to": "restart", "when": "the internet light is red or orange"},
         {"to": "resolved", "when": "all lights are green"}]},
      {"id": "restart", "kind": "instruct",
       "text": "Have the caller restart the router and wait 2 minutes.",
       "moves": [{"to": "resolved", "when": "the caller confirms it is back"}]},
      {"id": "resolved", "kind": "end", "text": "Confirm it works and close politely."}
    ]
  }
]
```

| Field | Means |
|-------|-------|
| `name` | How the model names the procedure when it reports a move. Lowercase letters, digits and `_` |
| `description` | When the procedure applies |
| `start` | `call`: running from the first turn. `on_request`: the model starts it when it applies |
| `window_depth` | How many steps ahead of the current one the model is shown (default 1, 0 for none) |
| `steps[].id` | The step's id, which moves name |
| `steps[].kind` | `ask`, `instruct`, `check`, `escalate` or `end` |
| `steps[].text` | What the model should do at the step |
| `steps[].start` | The step the procedure starts at |
| `steps[].tool` | A tool the model should call at the step |
| `steps[].moves` | The moves allowed from the step: `{to, when}`, `when` a plain-language condition the model judges |
| `steps[].escalate` | What an `escalate` step does: `{"transfer_call": {...}}` (the [transfer tool's](/guides/tools) fields) or `{"handoff_to_agent": {"agent_id": "..."}}` |

**The window.** Before each caller turn the model is given one message, right
before the turn and replacing the previous turn's: the current step and what
to do there, the allowed moves with their conditions, the move back to the
previous step, and a preview of the steps up to `window_depth` ahead. The
rest of the graph never enters the prompt.

```text
[Procedure]

Procedure "no_internet" — current step: restart (instruct)
  Do now: Have the caller restart the router and wait 2 minutes.
  Allowed moves:
    → resolved  when: the caller confirms it is back
    ← back to lights  (always allowed)
  Next steps (preview):
    resolved (end): Confirm it works and close politely.
  Report every move with move_to_step. Do not skip a step. If the caller's answer does not fit any move, ask again.
```

**Moves.** An agent with procedures is offered the built-in `move_to_step`
(`{procedure, to}`); it is never listed in `tools` (a `422` there). A move the
current step allows, or back to the previous step, is accepted: the procedure
moves and the result tells the model what to do at the new step. Anything
else is refused, the result naming the moves that are allowed and why, and the
procedure and its window stay where they were.

**Start modes and several procedures.** An agent can carry several
procedures, such as one per fault family. A `start: "call"` one runs from the
first turn. A `start: "on_request"` one lets the agent handle general
questions and run the procedure only when it applies: until it starts, the
prompt names it with its description and its start step's id, and no step's
text:

```text
## Procedures you can start
When one applies, start it with move_to_step(procedure=<its name>, to=<its start step>); its steps are then shown to you one at a time.
- no_internet: Caller has no internet connection at home (start step: lights)
- reset_password: Caller forgot the password to their account (start step: identify)
```

The model starts one with `move_to_step` to its start step; the result says
what to do there, and from the next turn its window is shown. A move in a
procedure that is not running is otherwise refused with the reason (an
`on_request` one's names its start step). The model is never shown the steps
of a procedure that is not running, and when several run, each has its own
window in the one message.

**Step tools and variables.** A step's `tool` names a tool the model should
call at that point, so an API check happens where it belongs and its result
informs the next move. The window says so, at the step and in the preview
(`after_restart (check, tool: line_status)`). It is one of the agent's own
`tools` (or a built-in, or `query_knowledge`) and runs like any other: it
reaches its webhook and is recorded in the call's tool invocations. Naming a
tool the agent does not have is a `422` naming the procedure and the step; an
agent with `mcp_servers` is not checked, since its MCP tools are only known
once a call connects. A step's `text` renders the call's
[template variables](#template-variables) like the rest of the config:

```json
{"id": "after_restart", "kind": "check", "tool": "line_status",
 "text": "Check the line status for {{account_id}}.",
 "moves": [{"to": "resolved", "when": "the line is fine"}]}
```

**Rules.** A procedure is checked when the agent is saved, so a mistake is a
`422` naming the procedure and the step rather than something found on a call:

- step ids are unique within the procedure, and procedure names within the agent;
- exactly one step has `start: true`;
- every move goes to a step that exists;
- every step can be reached from the start step by its moves;
- at least one step is of kind `end` or `escalate`;
- at most 50 steps, and `window_depth` at most 5.

```json
{"success": false, "code": "validation_error", "error": "Validation error",
 "details": {"errors": [{"msg": "Value error, procedures[0] 'no_internet': step 'after_restart' moves to 'technican', which does not exist", "...": "..."}]}}
```

A [call-init](/guides/call-init) inline agent skips that check, so the same
rule runs when its call is built: a broken procedure, or an entry that is not
a procedure at all, fails the call with `ended_reason: pipeline_error` and an
`error.raised` event naming the problem — never a call that runs without it.

Procedures are part of the agent's config, so they version, publish, roll back
and A/B-route with the agent, and a [call-init](/guides/call-init) inline
agent can carry its own. Cascade voice calls only: on an S2S agent they are
skipped, said on its read (`procedures_ignored_on_s2s`, below) and in the
build's log.

## Warnings on a Read

`GET /v1/agents/{id}` returns a **`warnings`** list beside the config: things
worth telling you about a config that must not be refusals, because refusing
them would break working agents.

```json
{
  "id": "...",
  "config": { "...": "..." },
  "warnings": [
    {
      "code": "pronunciations_unreadable",
      "message": "tts.pronunciations: elevenlabs (eleven_flash_v2_5) does not read pronunciation markup on model 'eleven_flash_v2_5', so these words are spoken as written: Metformin",
      "words": ["Metformin"]
    }
  ]
}
```

| Code | Means |
|------|-------|
| `pronunciation_looks_like_spelling` | A [pronunciation](/guides/providers#pronunciations) is the word typed back (`{"Metformin": "metformin"}`). Every character is legal IPA, so validation cannot refuse it — and it reaches the voice as real markup, so the word is now mispronounced *differently*. Ignore it if that really is the transcription |
| `pronunciations_unreadable` | The resolved TTS provider and model will not read the markup, so those words are spoken as written |
| `pronunciations_ignored_on_s2s` | `pipeline_mode: "s2s"` has no TTS stage for the markup to apply to |
| `knowledge_mode_unsupported` | A [knowledge base](/guides/s2s#knowledge-bases) is linked in `auto` mode to an S2S agent, which skips it: auto retrieval runs before each LLM turn, and a speech-to-speech model has no such point. Carries `modes` and `provider`. Link it in `tool` or `prompt` mode |
| `skills_ignored_on_s2s` | An S2S agent lists [skills](/guides/skills), which only cascade calls load; its calls run without them. Carries `skills` and `provider` |
| `procedures_ignored_on_s2s` | An S2S agent has [procedures](#procedures), which only cascade calls follow: the window goes before each caller turn, and a realtime model has no such point. Its calls run without them. Carries `procedures` and `provider` |

Warnings are **derived on every read**, never stored, so an agent whose model
moved out from under its pronunciations starts saying so without being edited.
An empty list means nothing to report.

## Template Variables

Personalize agents per-call using `{{variable}}` placeholders:

```json
{
  "system_prompt": "You are helping {{customer_name}}. Their account is {{account_id}}.",
  "first_message": "Hello {{customer_name}}!"
}
```

Variables are rendered at call start via [call-init](/guides/call-init) or the API, in a [skill's](/guides/skills) instructions and a [procedure](#procedures) step's text too. See [Server Events](/guides/server-events) for how to dynamically inject variables.

## Pipeline Mode

| Mode | Description | Processing | Caller-perceived turnaround |
|------|-------------|------------|-----------------------------|
| `cascade` (default) | STT → LLM → TTS | ~800ms | + `silence_timeout_ms` (default 800ms) |
| `s2s` | Speech-to-speech via single model | ~300ms | + `silence_timeout_ms` (default 800ms) |

Processing is the sum of each stage's time-to-first-byte. It is not what the
caller waits — the agent must first decide the turn has ended. With
`smart_turn_detection` on (the default) that decision is the model's, and VAD
waits only 0.2s; `silence_timeout_ms` is the window when Smart Turn is off, and
on S2S. See [Latency](/architecture#latency).

Set `pipeline_mode` in the agent config:

```json
{
  "pipeline_mode": "s2s",
  "s2s": {"provider": "openai", "voice": "alloy"}
}
```

See [Speech-to-Speech](/guides/s2s) for details.

## Voice Activity Detection

TurnCall uses **Silero VAD** for barge-in (interruption handling) and **Smart Turn V3** (ML-based, local ONNX) for accurate end-of-turn detection.

```json
{
  "interruption_enabled": true,
  "smart_turn_detection": true,
  "silence_timeout_ms": 800
}
```

### Spoken digits

Smart Turn judges a turn by how the caller *sounds* at its end, and a string of
digits — a phone, order or account number — often ends without the falling
intonation of a finished sentence. Measured on synthesized speech (8 voices),
utterances ending in a digit string were judged *incomplete* 14 times in 40;
plain sentences, 2 in 16 (both one robotic voice). An incomplete verdict is
not a stuck turn: the turn still ends once the caller has been silent for
`smart_turn_stop_secs` (default 1.0s), so the cost is that much extra wait
before the agent answers.

For an agent whose callers mostly read out numbers, any of these removes it:

- `stt.model: "flux-general-en"` — [Deepgram Flux](#deepgram-flux) decides the
  turn from the transcript as well as the audio.
- `smart_turn_detection: false` — the turn ends on `silence_timeout_ms` of
  silence alone. Lower that window with care: callers pause between digit
  groups.
- A lower `smart_turn_stop_secs` — keeps Smart Turn for everything else and
  shortens the wait it adds when it is unsure.

### Deepgram Flux

Flux is Deepgram streaming STT that detects the end of the caller's turn
itself. Pick a `flux-*` model on the `deepgram` provider — same account, same
key:

```json
{
  "stt": {
    "provider": "deepgram",
    "model": "flux-general-en",
    "keyterms": ["Acme"],
    "extra": {"eot_threshold": 0.7, "eot_timeout_ms": 5000}
  }
}
```

Flux then owns end-of-turn: the turn ends when Flux reports it, and its start
of turn is what interrupts the agent (unless `interruption_enabled` is false).
Smart Turn is not run for a Flux agent whatever `smart_turn_detection` says —
it would only wait again after Flux had decided — and `silence_timeout_ms` is
not used. Tune Flux with its own `eot_threshold` (confidence needed to end a
turn) and `eot_timeout_ms` (silence that ends one regardless) in `stt.extra`;
`min_confidence` and `language_hints` (for `flux-general-multi`) go there too.
Other keys are ignored. `stt.language` is not sent: `flux-general-en` is English
and `flux-general-multi` detects the language.

`eager_eot_threshold` (at most `eot_threshold`, e.g. `0.5`) starts the reply
early: when Flux predicts the turn is ending, the LLM starts answering, and the
answer is held until Flux confirms the turn — or dropped if the caller keeps
talking or the final transcript differs. The agent answers sooner by the gap
between the two, at the price of one extra LLM request for every prediction
Flux takes back. A tool call is never made on a prediction: it waits for the
confirmed turn.

Each turn's `metrics.turn` event (`GET /v1/calls/{id}/events?event_type=metrics.turn`)
carries `turn_end_ms`, the time from the caller going quiet to the turn being
called over — the number Flux shortens.

## Callers Who Go Quiet

A caller who puts the phone down without hanging up holds the line open. After
the agent finishes speaking, `user_idle_timeout_ms` of silence prompts it to
check in; a second consecutive silence ends the call with an `ended_reason` of
`customer_silent`. Speaking resets the count.

```json
{
  "user_idle_timeout_ms": 10000,
  "idle_message": "Are you still there?"
}
```

| Field | Default | Description |
|-------|---------|-------------|
| `user_idle_timeout_ms` | `10000` | Silence after the agent stops speaking before it nudges. `0` disables the guard entirely |
| `idle_message` | `"Are you still there?"` | What the agent says on the first timeout |

On cascade the line is spoken through TTS verbatim. S2S has no TTS stage, so
the model is asked to check in and words it itself — expect a paraphrase rather
than your exact string.

<Note>
  Not to be confused with `silence_timeout_ms`, the pause *within* a turn that
  decides you have finished your sentence. That one is measured in hundreds of
  milliseconds; this one in seconds, and only after the agent has spoken.
</Note>

A third case is neither timeout: a turn the VAD opened and closed with **no
transcript** — a cough, a door, a word nothing recognized. One that *interrupted*
the agent gets a single LLM run, so the agent asks the caller to repeat instead of
stopping dead mid-sentence. One that arrives while the agent was already waiting
is left unanswered, because replying to a passing truck is intrusive and the idle
guard above already covers a caller who has genuinely gone quiet. On by default,
and not configurable.

## Voicemail Detection

For outbound calls, detect voicemail and leave a message:

```json
{
  "voicemail_detection": {
    "enabled": true,
    "voicemail_message": "Hi, this is TurnCall. Please call us back at..."
  }
}
```

<Note>
  Voicemail detection cannot be combined with `pipeline_mode: "s2s"`.
</Note>

## Delete an Agent

```bash
curl -X DELETE http://localhost:8090/v1/agents/AGENT_UUID \
  -H "Authorization: Bearer tc_xxx"
```

Deleting archives the agent (any state): it stops answering calls and disappears from active use, while its call history, transcripts, and analyses remain queryable.
