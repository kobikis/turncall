Your server hears from TurnCall in two ways:

- **call-init** — a request TurnCall makes to your server URL before a call starts. Your answer picks the agent and fills its variables. It is the only event sent to a server URL.
- **webhook events** — everything that happens during and after a call (transcripts, tool results, transfers, failovers, the end of the call), delivered to the URLs you subscribe with `POST /v1/webhooks`. They are fire-and-forget: your response is ignored.

## call-init

Bind a phone number with `routing_target_type: "webhook"`:

```bash
curl -X POST http://localhost:8090/v1/phone-numbers \
  -H "Authorization: Bearer tc_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "external_number_sid": "PNxxx",
    "e164_number": "+15551234567",
    "routing_target_type": "webhook",
    "server_url": "https://your-server.com/turncall-events"
  }'
```

A WebRTC call takes `server_url` in the body of `POST /v1/webrtc/connect` instead. The request and the answer are described in [call-init](/guides/call-init).

## Webhook events

```bash
curl -X POST http://localhost:8090/v1/webhooks \
  -H "Authorization: Bearer tc_xxx" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://your-server.com/events", "events": ["*"]}'
```

`events` is a list of event types, or `["*"]` for all of them. The response carries the signing secret, once. To change the list later without changing the secret, use `PATCH /v1/webhooks/{id}` with a new `events`.

A subscription's `url` and a number's `server_url` must be `https://` outside development, or the request is a `422`. A Kubernetes Service in the same cluster (a host ending in `.svc` or `.svc.cluster.local`) may be `http://`; loopback and private addresses may not. See [Compliance](/guides/compliance#the-controls) for `ALLOW_PLAIN_HTTP_URLS`.

Every delivery is one envelope:

```json
{
  "event": "transcript.final",
  "project_id": "uuid",
  "call_id": "uuid",
  "agent_id": "uuid",
  "event_id": "uuid",
  "timestamp": "2026-10-12T17:40:43Z",
  "payload": {"role": "customer", "text": "Hello?"}
}
```

`event_id` is stable across retries: use it to drop a redelivery.

| Event | When |
|-------|------|
| `call.initializing` | The call is created, after call-init |
| `call.started` | An inbound call is about to be answered, or an outbound call was dialled (sent once; the callee answering adds none) |
| `transcript.final` | Each final utterance, the caller's or the agent's |
| `tool.result` | A tool call returned |
| `call.transferred` / `transfer.answered` | A transfer started / the transfer target answered |
| `call.agent_handoff` | The call moved to another agent |
| `provider.failover` | An STT, LLM or TTS moved to its backup |
| `skill.loaded` | The model loaded one of the agent's [skills](/guides/skills): `{skill, version, reason}` |
| `skill.unloaded` | A load past `max_loaded_skills` unloaded the skill loaded longest ago: `{skill, version, reason: "limit"}` |
| `error.raised` | A stage failed; the payload says which and why |
| `call.customer_silent` / `call.max_duration_reached` / `call.opted_out` | The idle guard, the duration cap, or a do-not-call request ended the call |
| `dtmf.sent` / `context.injected` | Keypad tones sent / a message added to the live call |
| `recording.ready` | The recording is stored |
| `call.failed` | The call could not be connected |
| `call.ended` | The call is over — with transcript, analysis and `ended_reason` |
| `call.rejected` | An inbound call refused over the live-call limit (no `call_id`) |
| `session.created` / `session.updated` / `chat.created` | Text conversations |
| `eval.run.started` / `eval.run.completed` | Eval runs |
| `campaign.started` / `campaign.completed` / `campaign.cancelled` | Campaigns |

`metrics.turn`, `delegation.completed` and `avatar.unavailable` (why a call's video Avatar did not show; see [Video Avatar](/guides/video-avatar)) are stored on the call's event log (`GET /v1/calls/{id}/events`) and never delivered.

Tool calls go to each tool's own `webhook_url` — see [Tools](/guides/tools).

`call.ended` carries `skills`, every skill the call resolved with its version and whether it was loaded (an empty list when the agent has none), as the call read does. See [Skills](/guides/skills#what-a-call-records).

`call.ended` carries the call's `retention`: how many days its recording, transcript and events are kept, `null` for good. See [Retention](/guides/retention).

## Redaction

If the project has [redaction](/guides/redaction) on, every webhook payload is redacted before it is sent, and a call's events before they are stored on its event log. A subscriber never sees a redacted value, and it cannot be recovered from the webhook, from a redelivery or from `GET /v1/calls/{id}/events`, which hold the same redacted payload. The one exception is a call that was live when redaction was turned on: see "A change applies to the next event" below.

A detected value is replaced by its type in angle brackets, and the rest of the text is kept:

```json
{
  "event": "transcript.final",
  "payload": {"role": "customer", "text": "Call me back on <PHONE_NUMBER> or at <EMAIL_ADDRESS>."}
}
```

- **Text, at any depth.** Every string in the payload is analysed: `text` on `transcript.final`, a tool's arguments and result on `tool.result`, a transfer's or a handoff's reason and message, an error's text, and in `call.ended` the `transcript`, `summary`, `analysis` (takeaways included) and the call's `metadata`. A JSON number of seven digits or more inside them is analysed as the digits it is written with, so `{"phone": 4155550132}` in a tool's arguments reads `{"phone": "<PHONE_NUMBER>"}`. The `session.*` and `chat.created` events of text conversations are redacted the same way. Campaign and eval-run events go through the same step.
- **Number fields, whole.** With `PHONE_NUMBER` chosen (it is in the default), the phone number fields at the top of a payload (`from_number`, `to_number` and the others, your own TurnCall number included) read `<PHONE_NUMBER>` when they hold a phone number. Which fields, and what happens to a value that is not a phone number (a WebRTC call's `"webrtc"`, a SIP address): [Number fields](/guides/redaction#number-fields).
- **Never analysed**: the envelope (`call_id`, `event_id` and the rest), and TurnCall's own fields at the top of a payload: ids, timestamps, statuses, `ended_reason`, `direction`, provider and model names, `tool_name`, URL fields such as `recording_url`, and numbers such as `duration_ms`. So you can still join an event to its call and dedupe it. Fields inside your own data (`metadata`, a tool's arguments, a takeaway) are analysed whatever they are called.

If you need a caller's number, read the call record: `GET /v1/calls/{id}` keeps `from_number` and `to_number`, and routing, the suppression list and campaigns use them as before. Redaction applies to what is stored and sent, not to the call itself.

**When the detector is unavailable**, text is withheld, never sent raw. If the detector fails to load, every string it would have analysed arrives as `<REDACTED>` for five minutes, and then the load is tried again; a server that falls far behind withholds text the same way rather than queue it. A number field that holds a phone number does not need the detector and still reads `<PHONE_NUMBER>`; one that holds anything else is withheld with the text. The event log holds `<REDACTED>` too, so the original cannot be read back later.

**A change applies to the next event.** Turning redaction on or off, or changing its types, applies at once on the server that took the change and within 30 seconds on the others. Events already sent are not sent again, and a call that was live during the change can have both kinds of payload. Its `call.ended` is sent after the change, but its `transcript` is the one stored on the call's event log: lines stored before redaction was turned on are sent as they were, unredacted.

**Not redacted:**

- **call-init and tool webhooks.** They are part of the live call, and your server answers them with the raw values: call-init receives the caller's number, and a tool's `webhook_url` receives the arguments the model gave it.
- **The recording.** Redaction is text only. `recording.ready` and `recording_url` point at the full audio; keep it briefly with a [retention](/guides/retention) policy.

## Signature Verification

All server events include HMAC-SHA256 signatures:

```
X-TurnCall-Signature: v1=<hex_hmac>
X-TurnCall-Timestamp: 1712345678
```

Verify by computing HMAC-SHA256 over `"timestamp.body"` with the signing secret: for call-init, the one returned when you bound the phone number; for webhook events, the one returned when you created the subscription. Compare in constant time, and refuse a timestamp more than five minutes old so a captured delivery cannot be replayed (a retry is sent within about two minutes, with its original timestamp and signature).
