A skill is what an agent needs for one task: a description of when to use it, the instructions to follow, the tools it calls and the knowledge bases it reads. You define it once in a project and version it the way you version an agent.

<Note>
Skills load on cascade voice calls. Text conversations, pinned versions and a limit on loaded skills are on their way.
</Note>

## Create a skill

```bash
curl -X POST http://localhost:8090/v1/skills \
  -H "Authorization: Bearer tc_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "verify_identity",
    "description": "Use before discussing anything account-specific: balance, bills, payments.",
    "instructions": "Ask for the date of birth and the last 4 digits of the account number. Call verify_customer with both. Never reveal an account detail before it returns verified=true.",
    "tools": [{
      "name": "verify_customer",
      "description": "Verify the caller against the account",
      "parameters_schema": {
        "type": "object",
        "properties": {"dob": {"type": "string"}, "last4": {"type": "string"}},
        "required": ["dob", "last4"]
      },
      "webhook_url": "https://crm.example.com/tools/verify",
      "webhook_secret": "a-secret-of-16-or-more-characters"
    }],
    "knowledge_bases": []
  }'
```

The response is version 1, a `draft`. Creating a skill with a name the project already has makes the next version of that skill, also a draft.

| Field | |
|-------|---|
| `name` | Lowercase letters, digits and underscores, starting with a letter or `_` (the shape of a tool name), at most 64 characters. Shared by every version of the skill, so it cannot be edited |
| `description` | When to use the skill, 1-1024 characters. The model chooses a skill by it |
| `instructions` | What to do once the skill is in use, 1-128,000 characters |
| `tools` | [Custom webhook tools](/guides/tools), in the agent's tool schema and under the agent's rules: a `webhook_url` (https outside development), an optional `webhook_secret` to sign each request. Names are unique within the skill, and a built-in's name (`end_call`, `transfer_call`, ...) is refused |
| `knowledge_bases` | Knowledge bases of the project, with the fields of an [agent's link](/guides/knowledge-base): `knowledge_base_id`, `mode`, `top_k`, `similarity_threshold`, `priority`, `tool_description` |

A refusal names what it refused: a tool by its place and name (`tools[1] 'get_invoices' webhook_url: ...`), a knowledge base outside the project by its place and id.

A tool's `webhook_secret` is encrypted at rest and every read returns it as `"***"`, as an agent's is.

## Lifecycle

Skills follow [agent versioning](/guides/agent-versioning):

| Request | |
|---------|---|
| `PUT /v1/skills/{skill_id}` | Edit a draft. Send only the fields to change: `description`, `instructions`, `tools`, `knowledge_bases`. A published or archived version is a `409` |
| `POST /v1/skills/{skill_id}/publish` | Make a draft the skill's live version. The previously published version of the same name is archived |
| `POST /v1/skills/{skill_id}/rollback` | Make an archived version live again. The current live version is archived |

A published version never changes; to change a live skill, create a new version, edit it, and publish it.

## List and read

```bash
curl "http://localhost:8090/v1/skills?name=verify_identity" \
  -H "Authorization: Bearer tc_xxx"
```

The list is newest first in the paginated envelope (`total`, `page`, `limit` up to 200). `name` lists one skill's versions, and `state` (`draft`, `published` or `archived`) filters by state: `?state=published` lists the live version of every skill. `GET /v1/skills/{skill_id}` reads one version.

Skills belong to their project: another project's skill is a `404` on every route.

## Attach skills to an agent

List the skills an agent may use by name in its config:

```json
{
  "system_prompt": "You are Maya, the support agent. Be brief and warm.",
  "skills": [{"skill": "verify_identity"}, {"skill": "explain_bill"}]
}
```

Each name resolves to the skill's live published version once, when a call starts, so a publish mid-call does not change a running call. A name with no published version in the project is skipped with a warning; the call goes on without it.

## Load a skill on a call

Until a skill is loaded the model sees only its name and description, in a section added to the system prompt, and a built-in tool, `load_skill`:

```text
You are Maya, the support agent. Be brief and warm.

## Skills you can load
Load a skill with load_skill when the conversation needs it. Its instructions and tools are added when you load it.
- verify_identity: Use before discussing anything account-specific: balance, bills, payments.
- explain_bill: Use when the caller asks why a bill changed.
```

None of the skills' tools are offered yet. When the conversation needs a skill the model calls `load_skill` with `{"name": "verify_identity"}`, and the skill's instructions join the prompt as their own section, its tools join the tool list, and the model answers with them:

```text
## Skill: verify_identity (v2)
Ask for the date of birth and the last 4 digits of the account number. ...
```

The conversation so far stays in the context: the caller does not repeat themselves. A load costs one more model response, once per skill per call.

A skill's instructions and its tools' descriptions render the call's [template variables](/guides/call-init#response-fields) (`{{name}}`), as the agent's own prompt does. Its webhook tools run like the agent's own, recorded in [tool invocations](/guides/tools).

When two tools share a name, the first of built-in, the agent's own tools, loaded skills' tools in load order, and MCP tools wins, in what the model is offered and in what runs. A skill tool with the name of one of the agent's tools is skipped.

An agent with no skills is given no section and no `load_skill`. Skills are not loaded on speech-to-speech agents.

## Audit

Every create, edit, publish and rollback is an [audit log](/guides/audit-log) entry with `resource_type: "skill"`. A publish or rollback also writes an `archived` entry for the version it took out of service.
