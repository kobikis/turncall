A skill is what an agent needs for one task: a description of when to use it, the instructions to follow, the tools it calls and the knowledge bases it reads. You define it once in a project and version it the way you version an agent.

<Note>
Skills load on cascade voice calls. Text conversations and pinned versions are on their way.
</Note>

## Create a skill

```bash
curl -X POST http://localhost:8090/v1/skills \
  -H "Authorization: Bearer tc_xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "verify_identity",
    "description": "Use before discussing anything account-specific: balance, bills, payments.",
    "instructions": "Ask for the date of birth and the last 4 digits of the account number. Call verify_customer with both. Never reveal an account detail before it returns verified=true.",
    "tools": [{
      "name": "verify_customer",
      "description": "Verify the caller against the account",
      "parameters_schema": {
        "type": "object",
        "properties": {"dob": {"type": "string"}, "last4": {"type": "string"}},
        "required": ["dob", "last4"]
      },
      "webhook_url": "https://crm.example.com/tools/verify",
      "webhook_secret": "a-secret-of-16-or-more-characters"
    }],
    "knowledge_bases": []
  }'
```

The response is version 1, a `draft`. Creating a skill with a name the project already has makes the next version of that skill, also a draft.

| Field | |
|-------|---|
| `name` | Lowercase letters, digits and underscores, starting with a letter or `_` (the shape of a tool name), at most 64 characters. Shared by every version of the skill, so it cannot be edited |
| `description` | When to use the skill, 1-1024 characters. The model chooses a skill by it |
| `instructions` | What to do once the skill is in use, 1-128,000 characters |
| `tools` | [Custom webhook tools](/guides/tools), in the agent's tool schema and under the agent's rules: a `webhook_url` (https outside development), an optional `webhook_secret` to sign each request. Names are unique within the skill, and a built-in's name (`end_call`, `transfer_call`, ...) is refused |
| `knowledge_bases` | Knowledge bases of the project, with the fields of an [agent's link](/guides/knowledge-base): `knowledge_base_id`, `mode`, `top_k`, `similarity_threshold`, `priority`, `tool_description` |

A refusal names what it refused: a tool by its place and name (`tools[1] 'get_invoices' webhook_url: ...`), a knowledge base outside the project by its place and id. What each mode does on a call is in [A skill's knowledge bases](#a-skills-knowledge-bases).

A tool's `webhook_secret` is encrypted at rest and every read returns it as `"***"`, as an agent's is.

## Lifecycle

Skills follow [agent versioning](/guides/agent-versioning):

| Request | |
|---------|---|
| `PUT /v1/skills/{skill_id}` | Edit a draft. Send only the fields to change: `description`, `instructions`, `tools`, `knowledge_bases`. A published or archived version is a `409` |
| `POST /v1/skills/{skill_id}/publish` | Make a draft the skill's live version. The previously published version of the same name is archived |
| `POST /v1/skills/{skill_id}/rollback` | Make an archived version live again. The current live version is archived |

A published version never changes; to change a live skill, create a new version, edit it, and publish it.

<Warning>
  Publishing or rolling back a skill changes every agent that follows its live version, on each agent's next call, without republishing those agents. [Who uses a skill](#who-uses-a-skill) lists them before you publish; [pin a version](#pin-a-version) to hold an agent back. See ADR-0030.
</Warning>

## List and read

```bash
curl "http://localhost:8090/v1/skills?name=verify_identity" \
  -H "Authorization: Bearer tc_xxx"
```

The list is newest first in the paginated envelope (`total`, `page`, `limit` up to 200). `name` lists one skill's versions, and `state` (`draft`, `published` or `archived`) filters by state: `?state=published` lists the live version of every skill. `GET /v1/skills/{skill_id}` reads one version.

Skills belong to their project: another project's skill is a `404` on every route.

## Attach skills to an agent

List the skills an agent may use by name in its config:

```json
{
  "system_prompt": "You are Maya, the support agent. Be brief and warm.",
  "skills": [{"skill": "verify_identity"}, {"skill": "explain_bill"}]
}
```

Each name resolves to the skill's live published version once, when a call starts, so a publish mid-call does not change a running call, and the next call runs whatever is live then.

### Pin a version

An entry may pin one version of the skill by its id, the `id` a skill read returns:

```json
"skills": [
  {"skill": "verify_identity"},
  {"skill": "payment_promise", "version_id": "4a73a31b-d797-4cfc-bf6c-bca5895c928b"}
]
```

A pinned entry runs exactly that version on every call, whatever is published or rolled back later. It still runs once a newer publish archives it; a draft cannot be pinned, since it can still change. The pin is an id rather than a version number because a rollback makes an older number live again, and an id always names the same version. To move a pinned agent to a newer version, change the pin in the agent's config.

Saving the agent (`POST /v1/agents`, `PUT /v1/agents/{agent_id}`) checks its skills against the version each resolves to now, and refuses with a `422` that names both sides:

| Refused | Message |
|---------|---------|
| A name the project has no skill of | `skills[0] 'nope' is not a skill in this project` |
| A name with only drafts: a call runs published versions only | `skills[1] 'draft_only' has no published version in this project; publish one first` |
| A skill tool named like one of the agent's own tools | `skills[1] 'explain_bill' tool 'get_invoices' collides with the agent's own tool 'get_invoices'` |
| Two listed skills with a tool of the same name | `skills[1] 'payment_promise' tool 'get_invoices' collides with skills[0] 'explain_bill' tool 'get_invoices'` |
| A name listed twice, pinned or not | `skills[1] 'explain_bill' is listed twice (first as skills[0])` |
| A pin naming no version in the project: an id that does not exist, or another project's | `skills[0] 'verify_identity' version_id '<id>' is not a version of a skill in this project` |
| A pin naming another skill's version | `skills[0] 'verify_identity' version_id '<id>' is a version of 'explain_bill', not of 'verify_identity'` |
| A pin naming a draft | `skills[0] 'verify_identity' version_id '<id>' is a draft (v3); pin a published or archived version` |

For a pinned entry the tools checked are the pinned version's, not the live one's. `details` carries the entry (`field`, `skill`; for a pin, `field` is `skills[i].version_id` and `version_id` is set) and, for a collision, `tool` and `collides_with`. `load_skill` is offered automatically, so listing it in the agent's own `tools` is refused too.

A skill version published after the agent was saved is not checked against it: a tool of that version whose name the agent already uses is skipped on the call, as is a skill an [inline call-init agent](/guides/call-init) names that has no published version, or pins a version that is not one of that skill's in the project.

## Who uses a skill

```bash
curl http://localhost:8090/v1/skills/verify_identity/agents \
  -H "Authorization: Bearer tc_xxx"
```

```json
[
  {"agent_id": "...", "agent_name": "collections", "agent_version": 3, "agent_state": "published",
   "skill": "verify_identity", "resolved_skill_id": "...", "resolved_version": 1, "pinned": true},
  {"agent_id": "...", "agent_name": "support", "agent_version": 7, "agent_state": "draft",
   "skill": "verify_identity", "resolved_skill_id": "...", "resolved_version": 2, "pinned": false}
]
```

Every draft and published agent version of the project that lists the skill, by agent name and version, with the skill version it resolves to now and `pinned`: for a pinned entry its pinned version, for any other the live published one, or `null` when none is published. This is who a publish or a rollback reaches: every entry with `pinned: false`. An archived agent version, a deleted agent's included, is not listed. A name the project has no version of is a `404`.

## Delete a skill

`DELETE /v1/skills/{skill_id}` deletes one version. While any agent version listed above names the skill, it is a `409` whose `details.agents` names them (`agent_id`, `name`, `version`, `state`), whatever the version deleted, pinned or not: an agent following the live version can be moved to any version of the skill by a publish or rollback, and a pinned one runs its version on every call. Remove the skill from their `skills` first. A deleted version is gone from every read; the calls that ran it keep their record of it.

## Load a skill on a call

Until a skill is loaded the model sees only its name and description, in a section added to the system prompt, and a built-in tool, `load_skill`:

```text
You are Maya, the support agent. Be brief and warm.

## Skills you can load
Load a skill with load_skill when the conversation needs it. Its instructions and tools are added when you load it.
- verify_identity: Use before discussing anything account-specific: balance, bills, payments.
- explain_bill: Use when the caller asks why a bill changed.
```

None of the skills' tools are offered yet. When the conversation needs a skill the model calls `load_skill` with `{"name": "verify_identity"}`, and the skill's instructions join the prompt as their own section, its tools join the tool list, and the model answers with them:

```text
## Skill: verify_identity (v2)
Ask for the date of birth and the last 4 digits of the account number. ...
```

The conversation so far stays in the context: the caller does not repeat themselves. A load costs one more model response, once per skill per call.

A skill's instructions and its tools' descriptions render the call's [template variables](/guides/call-init#response-fields) (`{{name}}`), as the agent's own prompt does. Its webhook tools run like the agent's own, recorded in [tool invocations](/guides/tools).

When two tools share a name, the first of built-in, the agent's own tools, loaded skills' tools in load order, and MCP tools wins, in what the model is offered and in what runs. A skill tool with the name of one of the agent's tools is skipped.

An agent with no skills is given no section and no `load_skill`. Skills are not loaded on speech-to-speech agents: an S2S agent that lists skills carries a `skills_ignored_on_s2s` entry in its read's `warnings`, and its calls run without them, logging why.

## A skill's knowledge bases

A skill's `knowledge_bases` take effect when it is loaded, by their `mode`:

| Mode | Once the skill is loaded |
|------|---|
| `prompt` | The documents' full text joins the skill's own section, after its instructions |
| `tool` | `query_knowledge` searches them. An agent with its own tool-mode knowledge base already offers it, and the same tool then searches the agent's and every loaded skill's. An agent without one is offered it by the load, with the hint to search before saying no |
| `auto` | Not applied: per-turn retrieval is built with the call, before any skill is loaded. Accepted at save, and every read of the skill carries a `knowledge_mode_unsupported` entry in its `warnings` naming the knowledge bases (`knowledge_base_ids`). `auto` is the default, so name `tool` or `prompt` |

```json
"warnings": [
  {
    "code": "knowledge_mode_unsupported",
    "message": "A knowledge base attached to a skill in 'auto' mode is not applied: ...",
    "modes": ["auto"],
    "knowledge_base_ids": ["6f1c..."]
  }
]
```

Before the load neither is in the prompt or searchable through the skill. A skill unloaded to make room (below) takes its documents out of the prompt and its knowledge bases out of the search. The documents are read when the call starts, with the skill, so a load reads nothing; a document added mid-call is in the next call. With several tool-mode knowledge bases, `top_k` and `similarity_threshold` come from the first searched: the agent's own, then the skills' in load order. A tool of the agent's, a skill's or an MCP server's named `query_knowledge` keeps the name, and the skills' knowledge bases are then not searchable.

## How many skills a call holds

`max_loaded_skills` in the agent config caps how many skills a call holds loaded at once: 3 by default, from 1 to 10.

```json
{
  "skills": [{"skill": "verify_identity"}, {"skill": "explain_bill"}, {"skill": "payment_promise"}, {"skill": "plan_change"}],
  "max_loaded_skills": 3
}
```

Loading a skill past the cap unloads the one loaded longest ago, in the same switch: its section leaves the prompt and its tools leave the tool list as the new skill's arrive, and the `load_skill` result tells the model which skill went. An unloaded skill stays in the list of skills the model can load, so it can load it again.

Loading a skill that is already loaded changes nothing: the result says it is already loaded, and the prompt and the tools stay as they are.

## Skills across a handoff

When a call is handed to another agent, with the `handoff_to_agent` tool or `POST /v1/calls/{id}/handoff`, the call takes that agent's skills: each resolved as at a call's start (its pinned or live published version in the call's project, rendered with the call's template variables), none loaded. The model is given the target agent's list and `load_skill` when it has skills, and neither when it has none. Skills the first agent loaded are not carried over, even when the target lists them too, and the target's own `max_loaded_skills` applies from then on.

## What a call records

The versions a call resolved are saved on the call when it starts, so the call stays explainable after a skill is published again. A handoff adds the target agent's versions. Each load is a `skill.loaded` event on the call's event log (`GET /v1/calls/{id}/events`), and each unload to stay within `max_loaded_skills` a `skill.unloaded` event with reason `limit`, recorded before the load that made room. Both are also delivered to [webhook subscribers](/guides/server-events#webhook-events):

```json
{"event": "skill.unloaded", "payload": {"skill": "verify_identity", "version": 2, "reason": "limit"}}
{"event": "skill.loaded", "payload": {"skill": "plan_change", "version": 1, "reason": "load_skill"}}
```

The call read (`GET /v1/calls/{id}` and the list) and `call.ended` carry `skills`: every skill version the call resolved, in the agent's order (after a handoff, the target agent's next; a version both agents resolved is listed once), with whether the agent pinned it and whether the call loaded it at any point. A skill the call never loaded is listed too, and a skill unloaded later still reads `loaded: true`: its `skill.unloaded` event says when it went. A call whose agent has no skills has an empty list.

```json
"skills": [
  {"skill": "verify_identity", "version": 2, "pinned": false, "loaded": true},
  {"skill": "explain_bill", "version": 1, "pinned": true, "loaded": false}
]
```

An eval run records neither. Skill names, versions and reasons are identifiers, never [redacted](/guides/redaction). `skill.loaded` and `skill.unloaded` are in the events kind of [retention](/guides/retention); once a call's events expire, `loaded` is `null`, and the versions stay.

## Audit

Every create, edit, publish, rollback and delete is an [audit log](/guides/audit-log) entry with `resource_type: "skill"`. A publish or rollback also writes an `archived` entry for the version it took out of service.
