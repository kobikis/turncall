# ADR-0028: pipecat 1.13 — delegation as a stream, and each minor on purpose

**Status:** Accepted
**Date:** 2026-10-20
**Supersedes:** nothing. Extends ADR-0019 (pipecat 1.12) and ADR-0006
(call.ended ordering). Tracked in #367.

## Context

pipecat 1.13.0 came out on 2026-10-19, and TurnCall's requirement allowed any
1.x: every install and image built from that day got it, and S2S delegation
broke (21 tests). #368 held pipecat below 1.13 until it was ported. Running the
full suite on 1.13 then found two more things the delegation tests did not:

- An `openai_live` agent with `llm.failover` would not build: 1.13's backend
  worker asks its LLM things an `LLMService` answers and TurnCall's
  `FailoverLLM` (a switcher) did not.
- A caller who hung up while the call's services were still connecting got
  `call.ended` 15 seconds late (the Asterisk integration tests).

The release is large (over 300 changelog entries). Most of it is fixes
TurnCall gets for nothing: TTS that went silent for the rest of a call when
metrics are on, the Telnyx serializer ending the call on a malformed message,
Silero ending a turn mid-word, STT that never failed over after a failed first
connect, and token counts — Anthropic's `prompt_tokens` doubled, Gemini's and
Grok's thinking left out — that ADR-0027's cost estimates will read. (Two
headline fixes do not apply: TurnCall's Twilio serializer is its own, and it
already resamples OpenAI Realtime's input to 24 kHz.)

## Decision

Take the bump whole, in one PR with no intended behaviour change beyond what
1.13 forces, as ADR-0019 did; adopt its new features in follow-ups (#372–#376).

**1. Client delegation is a stream, and TurnCall reads where it ends.** In 1.13
the live service attaches to the delegate once per call and puts each
delegation to it as a message; the delegate streams outputs, tool calls and,
when it has nothing left to do, idle. Delegations run one at a time, a later
one waiting. `delegation_events` was rebuilt on that:

- Every end goes through pipecat's `_finish_delegation`, where the outcome is
  read; a `BackendError` is seen in `_on_backend_event`, and a delegation that
  could not be put to the delegate in `_start_delegation`. The rest of 1.13's
  surface (the `ExternalFunctionCall*` frames, `transform_output`) says
  nothing about how a delegation ended, so a narrow private read stays, pinned
  by `test_pipecats_private_delegation_surface_is_still_there`.
- **`answered` is pipecat's own flag**: the delegate said something for the
  caller to hear. Its notes (unspoken output) are not an answer, so a run that
  wrote only notes is `failed`, as a run with no output was. No new outcome
  value. One exception carried over from #262: a delegation that ended the
  call did what it was asked, spoken or not.
- **The duration runs from creation**, so time spent waiting behind an earlier
  delegation counts — it is the caller's wait. A delegation the call's end
  drops records nothing, as before.
- **The single goodbye (#262) waits for the end of the delegation.** The
  delegate can say several things after its tool marks the call as ending;
  arming the hangup on the first, as before, would cut off the rest. What it
  says for the caller after the mark is held until the delegation finishes,
  then relayed as one, the gate armed once gpt-live-1 is quiet. The hold is
  bounded (5s after the first message): a delegate still working past it is
  stuck, and the caller should not sit in silence until the delegation's
  timeout. A delegation that started with the call already ending (waiting
  behind the one that ended it) did not end it, and is neither `answered` for
  that nor held.
- pipecat's own `_start_delegation` can finish the *next* delegation: one
  whose timeout fires while it waits for the delegate to attach is finished
  and the next started, then its start fails and finishes again. TurnCall
  ignores a finish from a start that is no longer the current delegation's.

CONTEXT.md, "Delegation outcome", is the definition.

**2. pipecat's pairing instruction is kept.** 1.13 appends
`BACKEND_PAIRING_INSTRUCTION` to the delegate's system prompt: it is the
backend of a voice assistant, the caller hears only what it marks with `>>`,
and how to take requests that arrive while it works. The `>>` mark is what
1.13 relays as spoken, so a TurnCall text would have to restate it; overriding
(`pairing_instruction`) is for when an eval shows it fighting #262's goodbye.

**3. `FailoverLLM` answers for its members.** `BackendLLMWorker` asks its LLM
whether it can be a backend, sets its reasoning to the provider's default,
appends the pairing instruction, and cancels its function calls when the
frontend lets go. The group forwards each to every member — a backup the call
fails over to is the same delegate — and refuses if any member would.

**4. A recording ends however the pipeline does.** 1.13 starts the input
transport while later processors are still setting up, and a pipeline
cancelled then sends no frame to a processor not yet started and no
`CancelFrame` to one that had. Both stranded the recording, and `call.ended`
sat out its 15-second recording wait:

- The recorder never started: its status stayed `none`, which post-call did
  not count as final. Post-call runs once the pipeline has finished (#356),
  when `none` can no longer change, so it is now final. `failed` was the
  alternative, rejected: no recording was attempted, and `failed` is a status
  someone investigates.
- It had started after the caller's disconnect flush had already run: the
  recorder now ends a recording still running at `cleanup()`, the one hook
  every processor gets. Its `in_progress` write, cancelled mid-way, could
  still land after that end, so it is written only over `none`.

**5. pipecat is capped at the next minor: `>=1.13.0,<1.14.0`.** A minor
rewrites internals TurnCall reaches into — delegation here, the judge in
1.12 — so each is adopted on purpose, with its changelog read, never picked up
by a fresh install. Patch releases still float, and so does everything else;
an authoritative lockfile is #377.

## Behaviour that changes with the bump, accepted

- **Reasoning defaults.** The Anthropic and Google services now send a model
  they list its lowest reasoning setting when the agent configures none (it
  was the provider's default), and log it: lower latency for a voice turn.
  (pipecat's OpenAI Responses service does too; no agent LLM uses it.) A
  client delegate runs at the provider's default.
- **Silero VAD 6.2.** Better on quiet voices and phone audio; a stop can come
  slightly later. Measured on 2026-10-20 (#305): on the same 32 clips, 6.2
  reports the stop ~60 ms later on clean speech and no later on phone-like
  audio (μ-law plus noise), and stops less than half as often inside a
  sentence — each such stop starts a Smart Turn decision on an unfinished
  one. End to end on stub providers (`make load-test`, one core, 1.12 and
  1.13 alternated), end of caller speech to first agent audio moved by
  +10–20 ms at p50 (~410 → ~430 ms) and not at all at p95. That is the
  pipeline's share; there is no caller-ear baseline to compare, since
  ADR-0023's PSTN harness is not built yet.
- **Pipeline start.** A processor holds the `StartFrame` only until its own
  setup is done, so the input transport reads audio while the LLM and TTS
  still connect, and `on_client_connected` (which starts the WebRTC greeting)
  can fire before they are ready. A frame queued then waits in order; the
  greeting is later, not lost.
- **Evals see the delegate's tool calls.** pipecat's harness reports the
  `ExternalFunctionCall*` frames as `function_call` events, so a scenario on an
  `openai_live` client delegate can assert them, and one expecting no
  `function_call` may change its verdict. `tool.called` / `tool.result` call
  events are TurnCall's own and unchanged. `SCHEMA_VERSION` moves to
  `pipecat-1.13`; 1.13 only added scenario fields.
- **RTVI.** `user-transcription`, `bot-llm-text` and `bot-tts-text` are
  deprecated (removed in 2.0); still sent. The web clients move later.

## Consequences

- The private read is in one method now, not spread across a per-delegation
  task, a context variable and a fallback sentence — but it is still private,
  and the contract test is what turns the next move into a red build.
- `FailoverLLM` carries a small `LLMService`-shaped surface it did not have.
  A 1.14 worker that asks its LLM something new fails the same way, at build;
  the delegate failover tests build one.

## Alternatives considered

**Re-point the old patches at 1.13's private names.** Rejected: the private
surface moved once and will again, and the old approach depended on more of it
(a task per delegation, a context variable, pipecat's fallback sentences).

**Move to `LLMWithBackend`.** Deferred: alpha, and `ClientDelegation` is still
how `OpenAILiveLLMService` takes a backend.

**A minor-version cap without the lockfile, or the lockfile now.** The cap is
here; the lockfile is #377, because the CPU-only torch install makes it a
packaging change of its own.

## Addendum: prompt caching on Claude (#374)

1.13's `AnthropicLLMService` takes `enable_prompt_caching` (pipecat#5887) and
`system_prompt_cache_ttl` (`"5m"`/`"1h"`, pipecat#5928). Without them every
turn of a Claude call re-sent the system prompt and tool list at full input
price and full time-to-first-token.

**Caching is on for every `anthropic` LLM a call builds**, in one place,
`pipeline_factory._create_llm_service`: the agent's, each `llm.failover`
member, an `openai_live` client delegate (built by the same
`_create_llm_stage`), and the voicemail classifier's. pipecat puts a
breakpoint at the end of the system prompt, which caches the tools ahead of it
too, and on the two latest user turns, which caches the conversation so far.
An `auto` knowledge base's passages sit in the messages, after the system
prompt, so moving them each turn costs the conversation's cache, never the
prompt's. Below the model's minimum cacheable length Anthropic caches nothing,
silently; nothing breaks.

**The text path does the same** (`llm_text._complete_text_anthropic`): the
system prompt goes as one text block with a breakpoint, so a turn's tool
rounds and the session's next message within five minutes read it back. The
conversation tail is not marked: SMS replies are often more than five minutes
apart, and a write nobody reads costs 1.25x. An `auto` knowledge base on text
puts its passages *ahead of* the prompt, so that prefix changes with every
message and is read back only by the same message's tool rounds. The stored
`token_count` adds the cached tokens back, since Anthropic reports
`input_tokens` net of the cache.

**TTL: Anthropic's default, five minutes, with no per-agent setting.**

- A call's turns come seconds apart and every read refreshes the entry, so
  within a call five minutes never lapses short of five minutes of silence,
  which the idle guard (on by default) ends first.
- The hour buys reuse *across* calls more than five minutes apart, at a write
  price of 2x the base input instead of 1.25x; it breaks even only at three
  requests on one entry, against two.
- The prefix is often the call's own: rendered `{{variables}}` and call-init's
  `knowledge_context` are in the system prompt, so the entry is read by that
  call alone and an hour would pay double for nothing. An agent whose prompt
  is the same for every call and is called more often than every five minutes
  shares one entry anyway, each call's reads keeping it warm.
- A setting would be a price trap with no measurement behind it. One can be
  added when an agent shows the gap it would fill.

**Measured** on 2026-10-20 with `scripts/measure_anthropic_cache.py`
(`claude-sonnet-5`, a ~3.5K-token prefix of prompt plus six tools, five
conversations of six turns per arm, the arms alternating):

| | turn 1 median | turns 2+ median (p90) | turns 2+ uncached input | turns 2+ cache read |
|---|---|---|---|---|
| off | 2031 ms | 1908 ms (2117) | 3710 tokens | 0 |
| on | 2010 ms | 2028 ms (2089) | 2 tokens | 3670 tokens |

The cache works: from turn 2 the whole prefix is read back and only the new
turn is billed at full price, so a six-turn conversation's input costs about
30% of what it did (one write at 1.25x, then reads at 0.1x). Time to first
token **did not move** at this size: Anthropic's latency swung between ~0.6 s
and ~2.2 s from one conversation to the next, both arms together, and that
swamps whatever reading 3.5K tokens from cache saves. Caching here is a cost
change, not a latency one; a prompt several times longer might show a
latency gain, and nothing here measured one.

Left open: Claude on `bedrock` (pipecat's `AWSBedrockLLMService` has its own
`enable_prompt_caching`, with cache points on Converse and per-model support);
`llm.warm_up` skipping Anthropic, where a warm-up would now also write the
cache before the first turn; the eval judge.

## Addendum (2026-10-20): the S2S greeting waits for the pipeline, not a clock (#373)

Realtime, Gemini Live and Nova Sonic got their opening `LLMRunFrame` after a
fixed `asyncio.sleep(2)`, a guess at how long the provider takes to connect.
On 1.13 `on_pipeline_started` is the answer: it fires once every processor's
`setup()` is done and the `StartFrame` has passed them all, and each of the
three connects (or starts connecting) in `setup()`. The greeting is queued on
it now. On a WebRTC call the peer's `on_client_connected` still triggers it, and
it then waits for the pipeline too, so it goes once both are up. A pipeline that
never starts leaves the greeting waiting until the call ends, when it is
cancelled. `openai_live` queues it at once, as before (#256).

The wait was not only for the greeting. Gemini Live and Nova Sonic finish
setting up their session on the first context, which is what that frame
delivers, and both drop the caller's audio until then. So the two seconds were
also two seconds in which the agent could not hear.

**Measured** on 2026-10-20, from `CallSession.start()` (where a carrier's media
stream hands over the call) to the event, through `build_call_pipeline` with
the real provider sockets and no database, as `turncall-demo` builds a call.
Ten alternating pairs per provider, `main`'s `_trigger_first_response` against
this one, on one developer machine:

| Provider | What | Before p50 (min–max) | After p50 (min–max) |
|---|---|---|---|
| OpenAI Realtime (`gpt-realtime-2.1`) | first agent audio | 2924 ms (2717–4964) | 1688 ms (1543–2052) |
| Gemini Live (`gemini-3.8-live`) | service takes the caller's audio | 2011 ms (2004–2420) | 511 ms (471–896) |
| Nova Sonic 2 | service takes the caller's audio | 2010 ms (2005–2246) | 23 ms (12–99) |

The pipeline started at p50 659 ms on Realtime, which connects inside
`setup()`, and at 7 ms and 16 ms on the other two, which connect in a
background task.

This is the pipeline's share, not ADR-0023's caller-ear number: no carrier
leg, one machine and one network. ADR-0023's PSTN harness is not built yet.
The carrier adds the same leg before and after, so the difference should
carry over.

**Found while measuring, not changed here:** Gemini Live and Nova Sonic do not
speak first on either branch. On Gemini, pipecat's adapter returns the system
instruction as a message for an empty context, so `_handle_context` skips the
developer-message seed it would otherwise add, and `_create_initial_response`,
which reads the bare context, finds nothing to answer. Nova Sonic 2 answers an
`LLMRunFrame` only when the context ends in a user message. Either way the agent
waits for the caller to speak.
